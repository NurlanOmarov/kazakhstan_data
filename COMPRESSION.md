# Сжатие базы данных

Замер сжимаемости этой базы: **zstd сжимает её в ~4.7 раза**
(1000 МБ → 212 МБ). Ниже три уровня — от безопасных правок до радикального
сжатия. Производительность нигде не страдает (а часто растёт).

## A. Оптимизации внутри БД — СДЕЛАНО

Применяется скриптом `optimize_db.py`:
- **Город/район ищутся точным совпадением** (значения берутся из
  автодополнения) → seek по индексу вместо скана. Быстрее.
- Удалён индекс `idx_addr_city` — точный фильтр города покрывается
  `idx_addr_neighbors(city, street, house)` по левому префиксу. **−0.4 ГБ**,
  без потери скорости.
- **FTS5 `optimize`** — слияние сегментов индекса: компактнее и быстрее MATCH.
- `VACUUM` — дефрагментация.

Эффект: меньше места + более быстрые фильтры адреса. Схема/код приложения
совместимы.

## B. Сжатый том файловой системы — РЕКОМЕНДУЕТСЯ для сервера

Самый сильный вариант «без потери производительности»: положить файл БД на
**Btrfs (или ZFS) со сжатием zstd**. SQLite работает как есть, страницы
распаковываются на лету (zstd ~1–2 ГБ/с на ядро — быстрее диска), горячие
данные кэшируются распакованными в RAM.

- **Место:** ~12 ГБ → **~2.5–3 ГБ** физически.
- **Скорость:** нейтрально или быстрее (меньше байт с диска).
- **Код менять не нужно.**

Готовый скрипт (Btrfs-том через loop-образ, работает на любом Linux):

```bash
sudo ./deploy/setup-compressed-volume.sh 16G
cp kazakhstan_data.db ./data/
docker compose up -d
```

ZFS-вариант (если на сервере ZFS):
```bash
zfs create -o compression=zstd -o mountpoint=/srv/kzdata tank/kzdata
cp kazakhstan_data.db /srv/kzdata/      # смонтировать как ./data
```

Проверить экономию: `compsize ./data` (пакет `btrfs-compsize`).

## C. sqlite-zstd — прозрачное сжатие внутри файла БД (опционально)

Если по какой-то причине нельзя использовать сжатую ФС (вариант B), можно
сжать данные **внутри самого файла** расширением
[`sqlite-zstd`](https://github.com/phiresky/sqlite-zstd).

- **Место:** файл БД ~12 ГБ → **~4–5 ГБ** на любой ФС.
- **Скорость:** небольшой расход CPU на чтение (при кэше почти незаметно).
- **Цена:** бинарное расширение (Rust), и БД нужно один раз преобразовать.

Приложение уже готово: при заданной переменной `KZ_SQLITE_ZSTD=/путь/к/расширению`
оно загружает расширение в каждое соединение (`app.py:data_conn`).

Шаги (один раз, на копии БД):
```bash
# 1) Собрать расширение (нужен Rust)
cargo install --git https://github.com/phiresky/sqlite-zstd sqlite-zstd-cli  # или сборка .so
#   получите libsqlite_zstd.so

# 2) Применить прозрачное сжатие к большим текстовым колонкам (на ЗАПИСЬ-копии)
sqlite3 kazakhstan_data.db <<'SQL'
.load ./libsqlite_zstd
SELECT zstd_enable_transparent('{"table":"residents","column":"Адрес","compression_level":9,"dict_chooser":"''a''"}');
SELECT zstd_incremental_maintenance(NULL, 1);
VACUUM;
SQL

# 3) Запускать сервис с расширением
KZ_SQLITE_ZSTD=/app/libsqlite_zstd.so docker compose up -d
```

> Примечание: вариант **B (сжатая ФС) предпочтительнее** — он даёт лучшее
> сжатие (~3 ГБ против ~4–5 ГБ), не требует бинарных расширений и проще в
> эксплуатации. C имеет смысл только если сжатую ФС поднять нельзя.
> B и C вместе использовать не нужно.

## Итог

| Вариант | Место | Скорость | Сложность |
|---|---|---|---|
| A (сделано) | −0.4 ГБ + дефраг | быстрее | — |
| **B: сжатая ФС** | **~3 ГБ** | нейтрально/быстрее | низкая ⭐ |
| C: sqlite-zstd | ~4–5 ГБ | чуть медленнее чтение | средняя |
